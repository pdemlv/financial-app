## 2. Безперервна інтеграція

### 2.1. Склад конвеєрів

Інтеграція розділена на чотири конвеєри. Поділ продиктований ризиком R6 дорожньої карти: швидкі перевірки блокують злиття, повільні винесені окремо, щоб не зупиняти роботу.

| Конвеєр | Де визначений | Тригер | Кроки | Бюджет часу |
| --- | --- | --- | --- | --- |
| `lint` | `ci.yml` | push і pull request у `master`, `develop` | `prisma generate`, `tsc --noEmit` | < 1 хв |
| `unit` | `ci.yml` | те саме, після `lint` | `npm run test:unit`, публікація звіту покриття | < 1 хв |
| `integration-api` | `ci.yml` | те саме, після `unit` | сервіс `postgres:16`, синхронізація схеми, `test:integration`, `test:api` | < 4 хв |
| `verify-staging` | `deploy.yml` | після деплою на staging і щоночі о 02:00 | `test:smoke`, далі `test:e2e`, збереження звіту Playwright | < 25 хв |

### 2.2. Принцип побудови

1. **Від дешевого до дорогого.** Конвеєри зʼєднані через `needs`: помилка типів зупиняє прогін за 40 секунд і не витрачає 4 хвилини на підняття бази даних.
2. **Ізоляція стану.** `integration-api` піднімає власний екземпляр `postgres:16` як сервіс-контейнер; тести не торкаються staging і не залежать від зовнішньої бази.
3. **Скасування застарілих прогонів.** Група `concurrency` скасовує попередній прогін тієї самої гілки, щоб черга не накопичувалась.
4. **Артефакти замість логів.** Звіт покриття і звіт Playwright зберігаються 14 днів, тому причину падіння видно без повторного запуску.

### 2.3. Критерії відмови

| Перевірка | Критерій | Джерело вимоги |
| --- | --- | --- |
| Типізація | `tsc --noEmit` без помилок | NFR-18 |
| Покриття | не менше 80 % рядків, гілок і функцій для `lib/services/calculations.ts` і `lib/format/money.ts` | NFR-18, задано в `jest.config.js` |
| Інтеграція і API | усі тести зелені за наявності `BASE_URL` | розділ 7.3 тест-плану |
| Smoke на staging | 10 з 10 перевірок SMK-01…SMK-10 | розділ 6 тест-плану |

### 2.4. Захист гілки

Злиття в `master` блокується, якщо червоний хоча б один із конвеєрів `lint`, `unit`, `integration-api`. Налаштовується через **Settings → Branches → Add rule**: `Require status checks to pass before merging` з переліком цих трьох перевірок і `Require a pull request before merging`. Конвеєр `verify-staging` має дорадчий статус і злиття не блокує — його падіння розбирається окремо, щоб нестабільність браузерних тестів не зупиняла розробку.

## 3. Середовища розгортання

| Середовище | Призначення | Розгортання | База даних | Хто має доступ |
| --- | --- | --- | --- | --- |
| Local | Розробка і налагодження | `npm run dev` на машині розробника | PostgreSQL у Docker, довільні дані | Розробник |
| Preview | Перевірка окремого pull request | Vercel, автоматично на кожен PR | Гілка БД Neon, створюється і видаляється разом з PR | Учасники PR |
| Staging | Приймальне тестування, e2e, ручні кейси | Vercel, автоматично з гілки `develop` | Neon, гілка `staging`, знеособлені дані | Розробник, тестувальник |
| Production | Робоча версія для користувачів | Vercel, з гілки `master` після ручного підтвердження | Neon, основна база з щоденними копіями | Розробник |

Середовища `staging` і `production` описані в GitHub як **Environments**, що дає два механізми: окремий набір секретів для кожного і правило `Required reviewers` для production, яке зупиняє конвеєр до ручного підтвердження.

## 4. Залежності розгортання

Порядок кроків при викочуванні визначений жорстко, бо його порушення призводить до помилок часу виконання:

1. **Збірка.** Застосунок збирається повністю до того, як на нього перемикається трафік. Невдала збірка не змінює стан середовища.
2. **Міграції бази даних.** `prisma migrate deploy` виконується **до** запуску нової версії коду. Нова версія може працювати зі старою схемою, стара з новою — ні.
3. **Запуск і перемикання трафіку.** Vercel перемикає трафік на готову збірку одним кроком.
4. **Перевірка.** Smoke-набір проти свіжого середовища.

**Правило зворотної сумісності міграцій.** Зміни схеми розбиваються на два релізи: спочатку додається нова структура (колонка, таблиця, індекс), і код починає її заповнювати; видалення старої структури виконується окремим наступним релізом, коли попередня версія коду вже не працює. Деструктивна міграція в одному релізі з кодом робить відкат неможливим — код відкотиться, а дані вже видалені.

**Зовнішні залежності:** Vercel (хостинг і CDN), Neon (керований PostgreSQL із гілкуванням і копіями), GitHub Actions (раннери `ubuntu-latest`). Збій будь-якої з них блокує розгортання, але не впливає на вже розгорнуту робочу версію.

## 5. Стратегія розгортання

**Обрана стратегія — атомарне розгортання з миттєвим відкатом** (immutable deployment). Кожна збірка отримує власну незмінну адресу; перемикання робочого домену на неї відбувається одним кроком, без проміжного стану, коли частина запитів обслуговується старою версією, а частина новою. Попередні збірки лишаються доступними, тому повернення — це перемикання вказівника, а не повторна збірка.

| Стратегія | Придатність для проєкту |
| --- | --- |
| **Атомарне перемикання (обрано)** | Відповідає моделі Vercel, не потребує додаткової інфраструктури, відкат — секунди, що з запасом вкладається в 10 хвилин NFR-16 |
| Blue-green | Дає ті самі гарантії, але вимагає двох постійних копій середовища і бази; надлишково для одного розробника |
| Canary | Потребує маршрутизації за частками трафіку і метрик для автоматичного рішення; обсяг аудиторії версії 1.0 не дає потрібної статистики |
| Rolling update | Має сенс для кількох екземплярів застосунку; монолітний деплой на Vercel їх не має |

## 6. Конвеєр доставки

| Крок | Staging | Production |
| --- | --- | --- |
| Тригер | push у `develop` | push у `master` |
| Підтвердження | не потрібне | обовʼязкове, `Required reviewers` |
| Резервна копія | не потрібна | перевірка свіжої копії за останні 24 години (NFR-15) |
| Міграції | гілка `staging` у Neon | основна база |
| Деплой | `vercel deploy` | `vercel deploy --prod` |
| Перевірка | `test:smoke`, далі повний `test:e2e` | `test:smoke` зі службовим акаунтом |
| Дія при невдачі | збірка не допускається до тестування | автоматичний `vercel rollback` |

## 7. Моніторинг

### 7.1. Що спостерігається

| Показник | Джерело | Поріг сповіщення | Вимога |
| --- | --- | --- | --- |
| Доступність застосунку | зовнішня перевірка `/api/health` щохвилини | недоступність понад 2 хвилини поспіль | FR-23 |
| Доступність бази даних | поле стану БД у відповіді `/api/health` | дві невдалі перевірки поспіль | FR-23 |
| Час завантаження сторінок | метрики Vercel, p95 | p95 понад 2 секунди протягом 10 хвилин | NFR-1 |
| Час відповіді API | метрики Vercel, p95 | перевищення порогу, визначеного в NFR-2 | NFR-2 |
| Частка помилок 5xx | логи платформи | понад 1 % запитів за 5 хвилин | NFR-17 |
| Незловлені винятки | трекер помилок (Sentry) | будь-яка нова помилка в production | NFR-17 |
| Свіжість резервної копії | звіт Neon | копія старша за 24 години | NFR-15 |

### 7.2. Принципи

1. **Моніторинг ззовні, а не зсередини.** Перевірка доступності виконується з іншої мережі: застосунок, який не працює, не може повідомити про себе сам.
2. **Сповіщення лише про дію.** Сповіщення надсилається тоді, коли потрібне втручання людини. Поодинокий 5xx записується в лог, але не піднімає тривогу.
3. **Логи без персональних даних.** Згідно з NFR-17 запис містить час, ідентифікатор запиту і стек виклику; сума операції, назва категорії й адреса пошти в лог не потрапляють.
4. **Кожен деплой позначений.** Версія збірки (SHA комміту) передається в трекер помилок, щоб зростання помилок одразу зіставлялося з конкретним релізом.

## 8. Повернення до стабільної версії

### 8.1. Порядок дій

| Крок | Дія | Час |
| --- | --- | --- |
| 1 | Виявлення: сповіщення моніторингу або падіння smoke-набору після деплою | до 2 хв |
| 2 | Рішення: якщо несправність зачіпає вхід, створення операції або показ балансу — відкат негайно, без діагностики причини | до 1 хв |
| 3 | Перемикання на попередню збірку: `vercel rollback` вручну або автоматично з `deploy.yml` | до 1 хв |
| 4 | Зворотна міграція бази, якщо реліз містив зміну схеми | до 5 хв |
| 5 | Контрольний smoke-набір проти відкоченої версії | до 2 хв |
| 6 | Розбір причини, виправлення в окремій гілці, повторний реліз | поза межами інциденту |

Сумарно кроки 1–5 вкладаються в 10 хвилин, що відповідає NFR-16.

### 8.2. Автоматичний відкат

Конвеєр `deploy.yml` виконує `vercel rollback` без участі людини, якщо smoke-набір на production завершився невдало. Автоматика охоплює найчастіший випадок — непрацездатність, помітну одразу після викочування. Поступова деградація (повільні відповіді, помилки в окремому сценарії) виявляється моніторингом і відкочується вручну.

### 8.3. Відновлення даних

Відкат коду не відновлює дані. Якщо реліз пошкодив записи, застосовується відновлення бази з копії Neon на момент часу до релізу (NFR-15, глибина 7 днів). Операція виконується лише після зупинки застосунку, щоб уникнути запису в базу під час відновлення.

## 9. Секрети і змінні середовища

Секрети зберігаються в GitHub Environments і налаштуваннях Vercel; у репозиторій вони не потрапляють (`doc/architecture.md`, розділ 8).

| Імʼя | Призначення | Де задається |
| --- | --- | --- |
| `DATABASE_URL` | Рядок підключення до Neon | Secret середовища, окремий для staging і production |
| `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` | Доступ до Vercel з конвеєра | Secret середовища |
| `STAGING_URL` | Адреса staging для e2e-прогону за розкладом | Secret середовища `staging` |
| `SMOKE_EMAIL`, `SMOKE_PASSWORD` | Службовий акаунт для smoke на production | Secret середовища `production` |
| `DEPLOY_ENABLED` | Вимикач конвеєра доставки | Repository variable |

## 10. Поточні обмеження

Стан на дату документа. Конвеєри написані так, щоб бути зеленими вже зараз і набувати сили в міру появи коду.

| Обмеження | Наслідок | Коли знімається |
| --- | --- | --- |
| Немає коду застосунку (Next.js ще не підключений) | `BASE_URL` не задається, integration- і API-тести пропускаються через `describeIfServer` | Етап M4 |
| Немає теки `prisma/migrations` | У CI використовується `prisma db push` замість `prisma migrate deploy` | Після першої міграції |
| ESLint і Prettier не встановлені | Job `lint` виконує лише перевірку типів; вимога NFR-18 покрита частково | Етап M4 |
| `DEPLOY_ENABLED` не встановлено | Конвеєр `deploy.yml` пропускається повністю | Після створення проєкту у Vercel і бази в Neon |
| Гілки `develop` немає | Шлях доставки на staging не задіяний | При переході до роботи з двома гілками |
