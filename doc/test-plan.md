## 1. Вступ

### 1.1. Мета

Документ визначає обсяг, підхід, середовища, тестові дані і критерії готовності для тестування версії 1.0. На його основі виконуються ручні тести, smoke-перевірки після кожного деплою та автоматизовані тести в CI.

### 1.2. Пов'язані артефакти

| Артефакт                                    | Розташування                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------- |
| Ручні функціональні тест-кейси              | `doc/tests/manual-functional.md` (50 кейсів, TC-F-01…TC-F-50)          |
| Ручні нефункціональні тест-кейси            | `doc/tests/manual-nonfunctional.md` (26 кейсів, TC-NF-01…26)           |
| Ручні тест-кейси користувацького інтерфейсу | `doc/tests/manual-ui.md` (29 кейсів, TC-UI-01…TC-UI-29)                |
| Smoke-набір                                 | `doc/tests/smoke-tests.md` (10 перевірок, SMK-01…SMK-10)               |
| Автоматизовані тести                        | `tests/` — unit, integration, api, e2e; інструкція в `tests/README.md` |
| Вимоги                                      | `doc/SRS.md`, `doc/backlog.md`, `doc/VISION.md`                        |
| Архітектура і API                           | `doc/architecture.md`                                                  |
| Специфікація дизайну і прототип             | `doc/design-spec.md`, `doc/ui/prototype.html`                          |

### 1.3. Обсяг тестування

**Тестується:**

- усі функціональні вимоги FR-1…FR-23, включно з S і C-пріоритетами (FR-5, FR-6, FR-17, FR-22, FR-23);
- нефункціональні вимоги NFR-1…NFR-24: продуктивність, безпека, зручність, сумісність, надійність, локалізація, доступність;
- відповідність інтерфейсу специфікації дизайну і прототипу;
- критерії прийняття AC1…AC11 з Vision документа.

**Не тестується (поза межами продукту, SRS 1.2):** мобільний застосунок, імпорт банківських виписок, мультивалютність, спільні акаунти, інвестиційний облік. Також не тестуються внутрішні механізми платформ Vercel і Neon — лише їхній результат для застосунку (доступність, резервні копії, rollback).

## 2. Підхід

### 2.1. Рівні тестування

Тести розподілені за пірамідою: найбільше швидких модульних тестів, менше інтеграційних і API, найменше повільних UI-сценаріїв. Розподіл відповідає шарам з `architecture.md`, розділ 3.1.

| Рівень      | Що перевіряє                                                                         | Інструмент                           | Каталог                   | Кількість       | Коли запускається                           |
| ----------- | ------------------------------------------------------------------------------------ | ------------------------------------ | ------------------------- | --------------- | ------------------------------------------- |
| Unit        | Чисті функції: розрахунок балансу і підсумків, валідація, форматування, rate limit   | Jest                                 | `tests/unit`              | 128             | Кожен push і pull request                   |
| Integration | API разом із PostgreSQL: що реально записано в БД, обмеження цілісності, каскади     | Jest, Supertest, Prisma              | `tests/integration`       | 23              | Кожен pull request (БД у Docker)            |
| API         | Контракт REST API: коди відповідей, формат помилок, ізоляція даних, безпека          | Jest, Supertest                      | `tests/api`               | 92              | Pull request, після деплою на staging       |
| UI e2e      | Сценарії користувача в браузері, адаптивність, клавіатура                            | Playwright                           | `tests/e2e`               | 57 × 4 браузери | Після деплою на staging, нічний прогін      |
| Smoke       | Базова працездатність (підмножина e2e з тегом `@smoke`)                              | Playwright                           | `tests/e2e/smoke.spec.ts` | 10              | Після кожного деплою (staging і production) |
| Ручні       | Функціональні, нефункціональні і UI-кейси, які складно або недоцільно автоматизувати | Чек-листи, DevTools, Lighthouse, axe | `doc/tests`               | 105             | Перед релізом, після значних змін           |

### 2.2. Типи тестування

| Тип                    | Як виконується                                                                                                       | Кейси                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |

| Класи еквівалентності  | Тип операції, формат суми (кома, крапка, пробіли, текст), формат email                                               | TC-F-04, 22; `tests/unit`                     |

| Зручність використання | Хронометраж внесення операції; тестування з 3–5 респондентами                                                        | TC-NF-12…14                                   |

| Регресійне             | Повний прогін автотестів + ручні кейси пріоритету M перед релізом                                                    | усі                                           |

### 2.3. Пріоритети тест-кейсів

Пріоритет кейсу успадковується від вимоги (MoSCoW): **M** — обов'язковий у кожному регресійному прогоні; **S** — перед релізом; **C** — за наявності часу. Для ручних кейсів у колонці «Авто» вказано, яким автотестом кейс покритий: такі кейси вручну виконуються лише при релізі, решта — при кожній регресії.

## 5. Критерії

### 5.1. Критерії входу (початок тестування етапу)

- Функціональність розгорнута на staging, CI-pipeline зелений (lint, build, unit, integration).
- Міграції БД застосовані, тестові акаунти і набори даних D0–D3 підготовлені.
- Smoke-набір на staging пройдений повністю — інакше збірка повертається розробнику без подальшого тестування.

### 5.2. Критерії виходу (готовність до релізу 1.0)

| Критерій                                                            | Поріг                                                                          |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Виконано ручних кейсів пріоритету M                                 | 100 %                                                                          |
| Пройдено ручних кейсів пріоритету M                                 | 100 % (або дефект відкладено з погодженням замовника)                          |
| Пройдено ручних кейсів S і C                                        | ≥ 90 %                                                                         |
| Автотести unit, integration, api в CI                               | 100 % зелені                                                                   |
| Автотести e2e на staging                                            | 100 % зелені у Chromium, ≥ 95 % в інших браузерах без відкритих Critical/Major |
| Покриття модульними тестами `calculations.ts` і `money.ts` (NFR-18) | ≥ 80 % (зараз 97–100 %)                                                        |
| Відкриті дефекти Critical / Major                                   | 0                                                                              |
| Відкриті дефекти Minor                                              | ≤ 5, усі з погодженим планом                                                   |
| Smoke на production після релізу                                    | 10 / 10                                                                        |
| Усі AC1–AC11 мають щонайменше один пройдений кейс                   | Так (матриця, розділ 10)                                                       |

### 5.3. Призупинення і відновлення

Тестування призупиняється, якщо: не проходить хоча б одна smoke-перевірка; staging недоступний понад 30 хвилин; знайдено Critical-дефект, що блокує понад 30 % кейсів. Відновлюється після виправлення і повторного успішного smoke-прогону.

## 6. Smoke-тестування

Smoke-набір із 10 перевірок (`doc/tests/smoke-tests.md`) підтверджує, що збірка придатна для подальшого тестування або для роботи користувачів. Набір автоматизований (`tests/e2e/smoke.spec.ts`, тег `@smoke`) і дублюється ручним чек-листом на випадок недоступності CI.

| Подія                       | Середовище | Режим                                                                      | Рішення при падінні                      |
| --------------------------- | ---------- | -------------------------------------------------------------------------- | ---------------------------------------- |
| Деплой гілки `develop`      | Staging    | `BASE_URL=<staging> npm run test:smoke`                                    | Збірка не приймається в тестування       |
| Деплой гілки `main`         | Production | `SMOKE_EMAIL=… SMOKE_PASSWORD=… npm run test:smoke` (SMK-03 пропускається) | Rollback до попереднього деплою (NFR-16) |
| Відновлення після інциденту | Production | Ручний чек-лист                                                            | Інцидент не закривається                 |

## 7. Автоматизація

### 7.1. Структура

```
tests/
├── unit/          # чисті функції lib/, без БД і HTTP (Jest)
├── integration/   # API + PostgreSQL: стан БД, обмеження цілісності (Jest + Supertest + Prisma)
├── api/           # контракт REST API (Jest + Supertest)
├── e2e/           # браузерні сценарії і smoke (Playwright)
└── helpers/       # клієнт API, фабрики користувачів, доступ до БД
lib/               # модулі, які покривають unit-тести: format, validation, services/calculations, auth/rate-limit
```

### 7.2. Запуск

| Команда                    | Що запускає                         | Змінні середовища                                            |
| -------------------------- | ----------------------------------- | ------------------------------------------------------------ |
| `npm test`                 | Unit                                | —                                                            |
| `npm run test:unit`        | Unit + звіт покриття з порогом 80 % | —                                                            |
| `npm run test:integration` | Integration                         | `BASE_URL`, `DATABASE_URL`                                   |
| `npm run test:api`         | API                                 | `BASE_URL`; `RUN_PERF=1` — тест NFR-2                        |
| `npm run test:e2e`         | Усі e2e у 4 проєктах Playwright     | `BASE_URL`                                                   |
| `npm run test:smoke`       | Smoke-набір                         | `BASE_URL`; для production — `SMOKE_EMAIL`, `SMOKE_PASSWORD` |

Без `BASE_URL` integration- і API-тести позначаються як пропущені, а не впалі, тому `npm test` зелений на машині без запущеного сервера.

### 7.3. Інтеграція з CI

| Job (`.github/workflows/ci.yml`) | Кроки                                                                                                        | Тривалість |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------- |
| `lint`                           | ESLint, Prettier, `tsc --noEmit`                                                                             | < 1 хв     |
| `unit`                           | `npm run test:unit`, публікація звіту покриття                                                               | < 1 хв     |
| `integration-api`                | Сервіс `postgres:16` → `prisma migrate deploy` → `next build && next start` → `test:integration`, `test:api` | < 4 хв     |
| `e2e` (окремий, R6 з ROADMAP)    | Після деплою на staging: `test:smoke`, потім `test:e2e`; артефакти — HTML-звіт і trace Playwright            | < 15 хв    |

Злиття в `main` блокується, якщо будь-який із перших трьох job червоний.

## 8. Дефекти

### 8.1. Життєвий цикл

`Новий → Підтверджений → У роботі → Виправлений → Перевірений → Закритий`; з «Підтверджений» можливі переходи `Відхилений` (не дефект / дубль) і `Відкладений` (з погодженням замовника). Перевірку виправлення виконує той, хто знайшов дефект; після неї повторно проганяються пов'язані кейси і smoke.

### 8.2. Серйозність

| Рівень   | Визначення                                                                 | Приклад                                                         |
| -------- | -------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Critical | Втрата або витік даних, неможливість основного сценарію, порушення безпеки | Користувач бачить операції іншого; баланс рахується неправильно |
| Major    | Функція працює неправильно, обхідний шлях незручний або відсутній          | Не працює фільтр за категорією; не зберігаються копійки         |
| Minor    | Відхилення без впливу на результат, є простий обхідний шлях                | Фільтри не зберігаються в адресі після перезавантаження         |
| Trivial  | Косметика                                                                  | Невірний відступ, неправильна форма слова «операцій»            |

### 8.3. Шаблон звіту про дефект (GitHub Issues, мітка `bug`)

```
Назва: [Область] Коротко, що не так — наприклад «[Операції] Сума 1 240,50 зберігається як 1 240,00»
Серйозність: Critical | Major | Minor | Trivial
Середовище: staging, build <commit sha>, Chrome 130 / Windows 11, ширина 1440
Тест-кейс / вимога: TC-F-26, FR-11, NFR-21
Передумови: акаунт qa.alice, набір D1
Кроки:
  1. ...
Фактичний результат: ...
Очікуваний результат: ...
Вкладення: скриншот, trace Playwright, HAR, рядок логу з requestId
```

## Додаток А. Шаблон ручного тест-кейсу

Кожен ручний кейс у `doc/tests/*.md` містить: **ID** (TC-F / TC-NF / TC-UI + номер), **назву**, **вимоги** (FR / NFR / US / AC), **пріоритет** (M / S / C), **передумови** (акаунт, набір даних, сторінка), **кроки**, **очікуваний результат** і **авто** — автотест, що покриває кейс (або «—»). Фактичний результат і статус фіксуються в журналі прогону, а не в самому кейсі, щоб кейс лишався незмінним між прогонами.

## Додаток Б. Контракт API, на який спираються тести

Доповнює таблицю з `architecture.md`, розділ 5. Суми — цілі числа в копійках, дати — рядки `РРРР-ММ-ДД`.

| Ендпоінт                          | Тіло успішної відповіді                                                                                     |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/register`         | `201` + сесійна cookie; тіло без `password` і `passwordHash`                                                |
| `POST /api/auth/login`            | `200` + сесійна cookie; `401` — `{ error: { message: "Неправильний email або пароль" } }` без `field`       |
| `GET /api/transactions`           | `{ items: Transaction[], nextCursor: string \| null }`, `limit` за замовчуванням 20                         |
| `POST`, `PATCH /api/transactions` | `Transaction`: `{ id, type, amount, categoryId, occurredAt, comment, createdAt, updatedAt }`                |
| `GET /api/categories`             | `{ items: [{ id, name, type, color, isDefault, transactionCount }] }`                                       |
| `GET /api/analytics/summary`      | `{ balance, income, expense, diff }`; без `from`/`to` — поточний місяць                                     |
| `GET /api/analytics/by-category`  | `{ total, items: [{ categoryId, name, color, amount, percent }] }`, «Інше» — останній, сума `percent` = 100 |
| `GET /api/analytics/timeline`     | `{ items: [{ month: "РРРР-ММ", income, expense, balance }] }`, кожен місяць періоду                         |
| `GET /api/health`                 | `{ status: "ok", db: "ok", version, dbLatencyMs }`; `503` — `db: "error"`                                   |
